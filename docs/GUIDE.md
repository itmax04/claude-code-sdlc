# Руководство: AI-native SDLC для Claude Code

Версия 1.0 · 2026-10-31 · Методология и то, как плагин `sdlc` её исполняет. Исходные материалы и аудит — [AUDIT.md](AUDIT.md),
устройство — [ARCHITECTURE.md](ARCHITECTURE.md).

## 1. Идея в пяти строках
1. **Человек** задаёт цель, границы, бюджет, риск и принимает результат. **Агент** превращает намерение в документы, код и
   доказательства. **Инструменты** (тесты, CI, хуки) дают свидетельства и ставят технические ограничения.
2. **Риск → процесс.** Строгость определяется последствиями ошибки (R0–R4), а не размером изменения.
3. **Один факт — один источник истины.** Требования — только в `spec.md`, состояние работы — только в `.sdlc/state.json`,
   решения владельца — в `intent.md`. Остальное ссылается, а не копирует.
4. **Состояние в Git, а не в памяти чата.** Любая новая сессия продолжает с того же места по файлам.
5. **Автономия до ворот.** Агент работает непрерывно и останавливается только там, где нужен человек: деньги, ключи, аккаунты,
   устройства, production, изменение цели и приёмка.

## 2. Маршрут
```text
survey → intent → spec → plan → build ↔ verify → review → release → maintain → (следующее изменение)
   ↑ incident — из любой фазы по реальному сигналу ─────────────────────────────┘
```
| Фаза | Вопрос | Выход (в `docs/changes/<ID>/`) | Кто проверяет |
|---|---|---|---|
| survey | Что есть на самом деле? | `.sdlc/survey.md` | агент |
| intent | Зачем и что? | `intent.md` (R0: `feature.md`) | владелец (брейншторм, решения Q-xx) |
| spec | Как должно себя вести? | `spec.md`: сценарии, R-xx, AC-xx со способом проверки | `sdlc:reviewer`; владелец при R3+ |
| plan | Как, в каком порядке, как откатить? | `plan.md`: шаги P-xx, ворота H-x, проверка, риски | `sdlc:reviewer` при R2+ |
| build | Реализовать малыми шагами | ветки, PR, `handoff.md` | CI + `sdlc:reviewer` на каждый PR |
| verify | Доказать каждый AC | `report.md` (PASS/FAIL/NOT RUN) | `sdlc:verifier` (не автор) |
| review | Готово ли изменение целиком? | `review.md` / раздел в report | `sdlc:reviewer` (свежий контекст) |
| release | Выпустить и уметь откатить | `release.md` | владелец выполняет production-шаги |
| maintain | Чему научились, что дальше? | закрытие изменения, улучшения harness | агент + владелец |
| incident | Остановить ущерб и не повторить | `incident.md` + регрессионный тест | агент; владелец — ключи/production |

Обратные связи: FAIL в verify и P0/P1 в review возвращают в build. Новое знание, меняющее требования, возвращает в spec —
с повторным согласованием, если меняется риск, стоимость или границы.

## 3. Профили риска
| | Признаки | Документы | Проверки | Ворота владельца |
|---|---|---|---|---|
| **R0** | текст, формат, обратимая мелочь | `feature.md` | релевантная проверка + свой diff | нет |
| **R1** | внутренняя функция, документы, инструменты | короткие intent/spec/plan | тесты, ревьюер на PR | по профилю проекта |
| **R2** | видно пользователю, общие данные, интеграции | полный набор, ADR | ревьюер на каждый PR, верификатор, CI | приёмка документов, если требует профиль |
| **R3** | ключи, авторизация, персональные данные, миграции, production, расход квот | + угрозы/приватность, rollback, release.md | + проверка безопасности, поэтапный выпуск | приёмка spec+plan; production — владелец |
| **R4** | необратимое, регулируемое | + аудит, учения по восстановлению | + второе независимое ревью | ворота на каждой фазе |

Маленькая задача может быть R3. При сомнении уровень повышают; понижают только с письменной причиной в intent.

## 4. Границы автономии
**Агент делает сам:** читает и исследует, пишет документы, код и тесты, запускает локальные проверки, работает в feature-ветках,
пушит их, открывает и обновляет PR и issues, вызывает ревьюера и верификатора, исправляет находки. Сливает PR только если в
проекте `merge_policy = agent` и выполнены условия: CI зелёный, ревьюер одобрил, доказательства AC записаны, ворота не блокируют.

**Только владелец** (агент создаёт ворота и даёт точные шаги на русском, а пока ждёт — делает независимую работу):
аккаунты, ключи, деньги, системные и консольные настройки, устройства и живые испытания, production и удалённые миграции,
удаление данных, переписывание истории, публикация вне репозитория, смена цели, объёма и бюджета, приёмочные ворота `H-*`.

**Вопросы владельцу** задаются только если ответ меняет объём, стоимость, риск или UX и его нет в источниках. Формат: 2–4
варианта, рекомендуемый первым, пачками. Молчание не согласие. Без владельца при R0–R1 допускается записанное допущение A-xx.

**Решение владельца** записывает только сам владелец командой `/sdlc:decide <ID> <ответ>`. Технически запись идёт хуком на текст,
набранный владельцем; модель не может её подделать (см. ARCHITECTURE §3).

## 5. Доказательства
Строка доказательства: `AC → версия (SHA) → среда → команда/наблюдение → ожидалось → получено → статус → ссылка`.
Статусы: PASS, FAIL, NOT RUN (почему и кто может выполнить), BLOCKED, N/A. Нельзя ослаблять тест ради зелёного результата и
писать «проверено» без запуска. Симулятор, мок или один удачный запрос не заменяют устройство. Самопроверка автора не заменяет
независимое ревью.

Серьёзность находок: **P0** ломает продукт, данные, секреты или жёсткое правило. **P1** — не выполнен AC, вероятная ошибка или
нет теста. Оба блокируют merge. **P2/P3** — по стоимости.

## 6. Как это исполняет Claude Code
| Принцип | Механизм |
|---|---|
| Одна команда запуска и продолжения | навык `/sdlc:run` (оркестратор) + процедуры фаз, которые загружаются по мере надобности |
| Состояние без памяти чата | `.sdlc/state.json` + `sdlc.py`; хук SessionStart подставляет статус в каждую новую или сжатую сессию |
| Работа без остановок до ворот | Stop-хук продолжает активный запуск, пока статус `in_progress` и есть прогресс; лимиты защищают от зацикливания |
| Независимая проверка | агенты `sdlc:reviewer` и `sdlc:verifier` в отдельном контексте без права редактировать файлы |
| Технические запреты, а не только текст | PreToolUse-хуки: force-push, push в защищённые ветки, `reset --hard`, удаление веток, секреты в файлах, защищённые пути, ночное окно для дорогих прогонов, запреты проекта; запись `state.json` только через скрипт |
| Решения владельца не подделать | `/sdlc:decide` + хук UserPromptSubmit |
| Экономия контекста | короткие описания навыков, фазы и справочники читаются по требованию, широкий поиск — агентом Explore |
| Параллельность по необходимости | независимые шаги плана — отдельные git worktree (`claude -w`); общая изменяемая область — последовательно |

Markdown объясняет правила, но не исполняет их. Критичные запреты продублированы в хуках и в `permissions.deny` проекта.
Ветки на GitHub Free для приватного репозитория не защищены, поэтому хуки — главный барьер.

## 7. Модели и effort
Основная сессия наследует модель и effort, выбранные владельцем. Для длинной автономной работы разумно начинать с Opus 5.5 и
`high`. Ревьюер работает с `high`, верификатор с `medium`; модель они наследуют. Фактическую модель и effort фиксируют в
handoff. Effort не заменяет недостающую информацию: сначала уточняют цель и доказательства.

## 8. Шаблоны
`plugins/sdlc/skills/run/templates/`: intent, spec, plan, feature (R0), handoff, report, review, release, incident, adr.
Заполняется только нужное. Пустые разделы удаляются, а не заполняются водой.

## 9. Чек-лист Definition of Done изменения
- [ ] intent принят (кем и когда), риск указан и обоснован
- [ ] каждый AC имеет способ проверки и строку в report.md
- [ ] все шаги плана слиты или явно отложены с причиной
- [ ] CI зелёный, ревьюер «approve», P0/P1 нет
- [ ] секрет-скан чист, правила языка и зависимостей соблюдены
- [ ] handoff.md и источники истины (README/архитектура/ADR/roadmap) обновлены
- [ ] ворота закрыты владельцем или явно перенесены
- [ ] отчёт владельцу отправлен в формате `reference/evidence.md`
